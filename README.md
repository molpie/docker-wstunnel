# wstunnel Docker Bastion

A minimal Docker image combining [wstunnel](https://github.com/erebe/wstunnel) and a hardened sshd, designed to act as a **secure bastion container** behind an nginx reverse proxy.

Wstunnel tunnels TCP traffic over WebSocket (or HTTP/2), allowing connections through firewalls and DPI by wrapping them in standard HTTPS traffic. The integrated sshd acts as a ProxyJump-only bastion: an attacker who breaks through wstunnel lands in an empty, restricted container with no shell, no tools, and no knowledge of your internal topology.

## Use Case

This setup enables SSH access to internal hosts through HTTPS port 443, useful when:

- Direct SSH (port 22) is blocked by a firewall or corporate proxy
- You need to reach internal hosts that are not directly exposed to the internet
- You want a hardened jump point that minimises blast radius if compromised

---

## Architecture

```
[your machine]
  wstunnel client
  ssh -J bastion internal-host
        │
        │ wss://443
        ▼
[nginx reverse proxy]
  location ^~ /wstunnel → proxy_pass :8080
        │
        │ ws://8080 (internal)
        ▼
[wstunnel + sshd bastion container]
  sshd port 2222 — ProxyJump only, no shell
        │
        │ SSH (internal network)
        ▼
[internal host]
```

The bastion container has no shell access, no private keys, no history, and a `PermitOpen` whitelist so it can only forward to explicitly defined hosts.

## Quick Start

```bash
# 1. Clone the repo and enter the directory
git clone https://github.com/youruser/wstunnel-bastion.git
cd wstunnel-bastion

# 2. Run setup: generates host keys, reminds you to place authorized_keys
sudo ./setup.sh

# 3. Copy your public key
cp ~/.ssh/id_rsa.pub ./config/authorized_keys
sudo chown 1000:1000 ./config/authorized_keys
sudo chmod 600 ./config/authorized_keys

# 4. Build and start
docker build -t molpie/docker-wstunnel:latest .
docker compose up -d
```

## Server Side

### Directory layout

```
.
├── Dockerfile
├── docker-compose.yml
├── entrypoint.sh
├── sshd_config
├── setup.sh
└── config/
    ├── authorized_keys          ← your SSH public key (uid 1000, mode 600)
    └── ssh_host_keys/
        ├── ssh_host_rsa_key     ← generated by setup.sh (uid 0, mode 600)
        ├── ssh_host_ecdsa_key
        └── ssh_host_ed25519_key
```

### setup.sh

Run once on the host before the first `docker compose up`. It generates sshd host keys with correct ownership and permissions, and reminds you to place `authorized_keys`.

```bash
sudo ./setup.sh
```

Key ownership rules:
- **Host keys** → `root:root` (uid 0), mode `600` — sshd refuses keys not owned by root
- **authorized_keys** → uid `1000` (jumpuser inside the container), mode `600`

### Dockerfile

Based on `alpine:3.23`. Downloads the official static wstunnel binary and installs openssh-server. No host keys are generated at build time — they are either mounted from the host or generated at container startup.

```dockerfile
FROM alpine:3.23

ARG WSTUNNEL_VERSION=10.5.5
ARG TARGETARCH

RUN apk add --no-cache ca-certificates tar openssh-server && \
    case "${TARGETARCH}" in \
      amd64) ARCH="amd64" ;; \
      arm64) ARCH="arm64" ;; \
      arm)   ARCH="armv7" ;; \
      *) echo "Unsupported arch: ${TARGETARCH}" && exit 1 ;; \
    esac && \
    wget -qO /tmp/wstunnel.tar.gz \
      "https://github.com/erebe/wstunnel/releases/download/v${WSTUNNEL_VERSION}/wstunnel_${WSTUNNEL_VERSION}_linux_${ARCH}.tar.gz" && \
    tar -xzf /tmp/wstunnel.tar.gz -C /usr/local/bin wstunnel && \
    chmod +x /usr/local/bin/wstunnel && \
    rm /tmp/wstunnel.tar.gz && \
    adduser -D -u 1000 -s /sbin/nologin jumpuser && \
    passwd -d jumpuser && \
    mkdir -p /home/jumpuser/.ssh && \
    chmod 700 /home/jumpuser/.ssh && \
    chown jumpuser:jumpuser /home/jumpuser/.ssh

COPY sshd_config /etc/ssh/sshd_config
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

EXPOSE 8080

ENTRYPOINT ["/entrypoint.sh"]
```

### entrypoint.sh

Generates sshd host keys only if not already present (i.e. not mounted from an external volume), then starts sshd and wstunnel. All wstunnel arguments are passed via `docker compose` `command:`.

```bash
#!/bin/sh
set -e

for keytype in rsa ecdsa ed25519; do
    keyfile="/etc/ssh/ssh_host_${keytype}_key"
    if [ ! -f "$keyfile" ]; then
        echo "INFO: Generating host key: $keytype"
        ssh-keygen -t "$keytype" -f "$keyfile" -N "" -q
    else
        echo "INFO: Using existing host key: $keytype"
    fi
done

echo "INFO: Starting sshd on port 2222..."
/usr/sbin/sshd

echo "INFO: Starting wstunnel..."
exec wstunnel "$@"
```

Mounting host keys from an external volume keeps the sshd fingerprint stable across container restarts, so clients do not need to update `known_hosts` on every redeploy.

### sshd_config

```
Port 2222
Protocol 2

PasswordAuthentication no
PubkeyAuthentication yes
AuthorizedKeysFile /home/jumpuser/.ssh/authorized_keys

# ProxyJump requires AllowTcpForwarding yes (uses ssh -W internally)
AllowTcpForwarding yes
# Restrict forwarding destinations to known internal hosts only
PermitOpen 10.0.0.10:22 10.0.0.11:22

PermitTTY no
X11Forwarding no
PermitTunnel no
GatewayPorts no
AllowAgentForwarding no
PermitUserEnvironment no
IgnoreRhosts yes

KexAlgorithms curve25519-sha256,curve25519-sha256@libssh.org
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com
MACs hmac-sha2-256-etm@openssh.com,hmac-sha2-512-etm@openssh.com

AllowUsers jumpuser

PrintMotd no
ClientAliveInterval 30
ClientAliveCountMax 3
LoginGraceTime 20
```

`PermitOpen` is the most important restriction: it limits ProxyJump destinations to an explicit whitelist, so even if the container is compromised an attacker cannot pivot to arbitrary hosts on your network.

> Remove `PrintLastLog` entirely — it is not supported by OpenSSH 10.x on Alpine and causes a warning at startup.

### docker-compose.yml

```yaml
services:
  wstunnel:
    image: molpie/docker-wstunnel:latest
    container_name: wstunnel
    cap_drop:
      - ALL
    cap_add:
      - SETUID        # sshd privilege separation
      - SETGID        # sshd privilege separation
      - SYS_CHROOT    # sshd privsep chroot /var/empty
    security_opt:
      - no-new-privileges:true
    read_only: true
    tmpfs:
      - /tmp
      - /run/sshd
    ports:
      - "8080:8080"
    volumes:
      - "./config/authorized_keys:/home/jumpuser/.ssh/authorized_keys:ro"
      - "./config/ssh_host_keys/ssh_host_rsa_key:/etc/ssh/ssh_host_rsa_key:ro"
      - "./config/ssh_host_keys/ssh_host_ecdsa_key:/etc/ssh/ssh_host_ecdsa_key:ro"
      - "./config/ssh_host_keys/ssh_host_ed25519_key:/etc/ssh/ssh_host_ed25519_key:ro"
    command:
      - server
      - "ws://0.0.0.0:8080"
      - --restrict-to
      - "127.0.0.1:2222"
```

Notable hardening applied at compose level:
- `cap_drop: ALL` then explicit `cap_add` for only what sshd needs
- `no-new-privileges: true` — no process can gain additional privileges
- `read_only: true` — container filesystem is immutable; tmpfs covers the two writable paths sshd needs
- Host keys and `authorized_keys` mounted read-only

## Nginx Configuration

nginx handles TLS termination. wstunnel listens on plain `ws://` internally. The `location ^~ /wstunnel` block must be declared before any catch-all location to ensure correct routing priority. `proxy_buffering off` is required for WebSocket streaming.

```nginx
server {
    listen 443 ssl;
    server_name your-server.example.com;

    ssl_certificate     /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    location ^~ /wstunnel {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }

    location / {
        # your existing config
    }
}
```

The `^~` modifier ensures this location takes precedence over regex-based locations. If your vhost uses any authentication middleware, the `/wstunnel` location must be declared before it — middleware that redirects unauthenticated requests (e.g. HTTP 302 to a login page) will break the WebSocket upgrade.

> **Note**: if nginx is running in Docker, use the container IP or Docker network hostname instead of `127.0.0.1` in `proxy_pass`.

## Client Side

Install wstunnel on your local machine from the [releases page](https://github.com/erebe/wstunnel/releases).

### Basic usage — direct SSH via ProxyJump

```bash
# 1. Start the wstunnel client (forwards local :2222 → bastion sshd :2222)
#    --http-upgrade-credentials is a CLIENT-side parameter only
wstunnel client \
  -L tcp://2222:127.0.0.1:2222 \
  -P wstunnel \
  --http-upgrade-credentials myuser:mypassword \
  wss://your-server.example.com:443

# 2. SSH to an internal host via ProxyJump through the bastion
ssh -J jumpuser@localhost:2222 ubuntu@10.0.0.10
```

### ~/.ssh/config — recommended setup

```
Host bastion
    HostName localhost
    Port 2222
    User jumpuser
    IdentityFile ~/.ssh/id_rsa

Host internal-oci1
    HostName 10.0.0.10
    User ubuntu
    IdentityFile ~/.ssh/id_rsa_internal
    ProxyJump bastion

Host internal-oci2
    HostName 10.0.0.11
    User ubuntu
    IdentityFile ~/.ssh/id_rsa_internal
    ProxyJump bastion
```

Then simply:

```bash
ssh internal-oci1
```

### Parameters explained

| Parameter | Description |
|-----------|-------------|
| `-L tcp://2222:127.0.0.1:2222` | Listen on local port 2222, forward to bastion sshd port 2222 |
| `-P wstunnel` | HTTP upgrade path prefix — must match the nginx `location` path |
| `--http-upgrade-credentials` | Basic auth credentials — **client-side only**, validated by wstunnel server |
| `-p http://[user:pass@]host:port` | Route through a corporate HTTP proxy |
| `wss://` | WebSocket over TLS — always use when nginx handles TLS termination |

> **Important**: the server URL must not include a path (`wss://host:443`, not `wss://host:443/wstunnel/`). The path is controlled exclusively by `-P`.

### Behind a corporate HTTP proxy

```bash
# Without proxy authentication
wstunnel client \
  -L tcp://2222:127.0.0.1:2222 \
  -P wstunnel \
  -p http://proxy.corp.example.com:8080 \
  wss://your-server.example.com:443

# With proxy authentication
wstunnel client \
  -L tcp://2222:127.0.0.1:2222 \
  -P wstunnel \
  -p http://proxyuser:proxypassword@proxy.corp.example.com:8080 \
  wss://your-server.example.com:443
```

Via environment variable:

```bash
export HTTP_PROXY=http://proxyuser:proxypassword@proxy.corp.example.com:8080
wstunnel client -L tcp://2222:127.0.0.1:2222 -P wstunnel wss://your-server.example.com:443
```

If proxy credentials contain special characters, percent-encode them (`@` → `%40`, `#` → `%23`).

wstunnel connects to the corporate proxy using HTTP `CONNECT`. The WebSocket upgrade happens inside that tunnel, so the proxy sees only a standard HTTPS connection to port 443.

### SSH ProxyCommand (no local port)

```
# ~/.ssh/config
Host myserver-tunnel
    HostName your-server.example.com
    User jumpuser
    ProxyCommand wstunnel client --log-lvl=off \
      -L "stdio://127.0.0.1:2222" \
      -P wstunnel \
      wss://your-server.example.com:443

# Behind a corporate proxy
Host myserver-tunnel-corp
    HostName your-server.example.com
    User jumpuser
    ProxyCommand wstunnel client --log-lvl=off \
      -L "stdio://127.0.0.1:2222" \
      -P wstunnel \
      -p http://proxyuser:proxypassword@proxy.corp.example.com:8080 \
      wss://your-server.example.com:443
```

## Security Considerations

### Threat model

The bastion design contains the blast radius of a wstunnel compromise. An attacker who successfully establishes a tunnel reaches only the sshd inside the container, which enforces:

- Public key authentication only — no passwords
- `PermitTTY no` — no interactive shell
- `PermitOpen` whitelist — ProxyJump destinations are limited to explicitly defined hosts
- `/sbin/nologin` shell for jumpuser — connection closes immediately if a shell is somehow requested
- Read-only container filesystem — no tools can be written or executed

| Risk | Severity | Mitigation |
|------|----------|------------|
| Unauthenticated access to `/wstunnel` path | Medium | `--http-upgrade-credentials` on server and client |
| Brute-force SSH through tunnel | Medium | Keys only, `MaxAuthTries 3`, fail2ban/crowdsec on sshd port |
| Container escape to host | Low | `cap_drop ALL`, `no-new-privileges`, `read_only` |
| Pivot to arbitrary internal hosts | Low | `PermitOpen` whitelist in sshd_config |
| Outdated wstunnel binary | Low–Medium | Pin `WSTUNNEL_VERSION`, monitor releases |
| Stable fingerprint leak across restarts | Info | Mount host keys from volume (setup.sh handles this) |

### SSH hardening on internal hosts

The bastion is only as strong as the hosts behind it. Ensure internal hosts enforce:

```
# /etc/ssh/sshd_config on internal hosts
PasswordAuthentication no
PermitRootLogin no
MaxAuthTries 3
```

### Capabilities rationale

| Capability | Why needed |
|------------|------------|
| `SETUID` | sshd privilege separation |
| `SETGID` | sshd privilege separation |
| `SYS_CHROOT` | sshd privsep chroot into `/var/empty` |

All other capabilities are dropped. `no-new-privileges: true` prevents any process from acquiring additional capabilities at runtime.
